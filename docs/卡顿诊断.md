# 房间卡顿诊断（D20261111-fish-007）

> 现象：老大在 DSH 里点顶部「房间」图标能看到画面了，但「还是很卡」（原话 2026-11-11 21:57）。
> 本单只查根因 + 出方案，没改外观、没重启 DSH。
> 测量时间：2026-11-11 22:00–22:20，窗口 1264×805 / devicePixelRatio 1，ego Chromium（与 DSH 同为 Electron/Chromium 内核）。

---

## 0. 一句话结论

**卡是填充率（GPU 像素着色）受限，不是 CPU/主线程受限。** 最大的单笔开销是 1264×805 的整屏像素着色 × 每帧 961 次 draw call，跑在**核显 Intel UHD Graphics**（不是 RTX 3060 独显）上。把 canvas 背存缩小到 1/2 线性尺寸，帧率从 **17 fps → 34.7 fps**（翻倍）；缩小到 1/4，稳定在 **35.3 fps 上限**（此时已经和像素数无关，撞到别的瓶颈）。JS 每帧只花 **p50 0.1 ms / avg 3.5 ms**，GPU 纯渲染查询 **p50 0.90 ms** —— 主线程完全不累，累的是核显。

## 3. 渲染负载量化

### 3.1 每帧 draw call 与三角数（hook `gl.drawElements` / `gl.drawArrays`）

| 项 | 值 |
| --- | --- |
| **draw call / 帧** | **961** |
| 三角数 / 帧 | 72,589 |
| `bindFramebuffer` 切换 / 帧 | 0（阴影贴图走 renderTarget，不进默认 framebuffer 计数） |
| 相机 | 固定机位（单相机，无多视图） |

### 3.2 CPU 侧 JS 耗时（hook rAF 回调）

| 指标 | 值 |
| --- | --- |
| p50 | **0.10 ms** |
| p95 | 8.0 ms |
| max | 9.9 ms |
| avg | 3.52 ms |

一帧 78 ms，JS 只花 0.1–3.5 ms。**CPU 主线程占用 < 5%，完全不是瓶颈。**

### 3.3 GPU 侧纯渲染耗时（`EXT_disjoint_timer_query_webgl2`，包住 clear→drawElements）

| 指标 | 值 |
| --- | --- |
| 样本数 | 58 |
| p50 | **0.903 ms** |
| p95 | 1.006 ms |
| max | 1.081 ms |

**这个数字很关键**：GPU 命令队列报的「GPU 执行时间」只有 0.9 ms，但实际帧要 78 ms。说明核显在 **命令提交/上下文切换/同步** 上等，而不是执行着色器本身 —— 典型核显 + 大 draw call 数 + 大分辨率下的驱动开销。也就是说：**减少 draw call 数比减少三角形数更有效**。

| 项 | 值 | 出处 |

## 4. 分场景对比（三态）

| 场景 | 帧率 | 房间 node 进程 CPU | DeepSeek 进程 CPU（10s 内） | chrome CPU | 说明 |
| --- | --- | --- | --- | --- | --- |
| **① DSH 面板开着** | 老大反馈「很卡」（未取到帧数，我进不去 DSH 页面） | — | — | — | 同源 iframe 跑在 DeepSeek 渲染进程里 |
| **② 收起 / 无页面** | 不渲染（`__fishRoomRenderPause` 后 tick 归零） | **0.0–0.2 CPU-s/10s**（≈0.2% 单核） | 8.58 CPU-s/10s（DSH 自身空闲开销） | 1.89 CPU-s/10s | 房间 node 进程几乎不占 CPU，只做 1.2 s 轮询 |
| **③ 浏览器直开 13100** | **12.8–19.2 fps**（balanced）/ 18–19.2（low） | 同上 | 6.66 CPU-s/10s | **7.61 CPU-s/10s**（渲染中） | 与 DSH 同架构 Chromium |

**判定**：三种状态下**都卡**。②→③ 之间 chrome 多用了 5.7 CPU-s/10s，说明渲染成本真实存在；DSH 面板（①）与浏览器直开（③）跑的是同一套 WebGL，同样落在 Intel UHD 上，**所以「DSH 特有」这个假设不成立** —— 不是 Electron 嵌套 iframe 的锅，是这台机器用核显跑 96 万像素 × 961 draw call 的锅。

### 4.1 填充率实验（最硬的证据）

在同一页面、不改任何代码，只改 canvas 背存尺寸（`canvas.width/height`）：

| canvas 背存 | 像素数 | 帧率 | 相对 |
| --- | --- | --- | --- |
| 1264×805 | 1,017,520 | **17.0 fps** | 基准 |
| 632×403（1/2 线性 = 1/4 像素） | 254,696 | **34.7 fps** | **+104%** |
| 316×201（1/4 线性 = 1/16 像素） | 63,517 | **35.3 fps** | 撞上限，与像素数脱钩 |

**帧率随像素数近似反比变化** = 教科书级的 fill-rate bound。1/4 像素时到了 35 fps 就上不去了，那是另一层瓶颈（核显的上下文/同步开销 + 无合批的 961 draw call）。

### 4.2 阴影代价

| 配置 | draw call/帧 | 帧率 |
| --- | --- | --- |
| balanced（shadowMap 开，2048²） | 961 | 12.3 fps |
| low（shadowMap 关，1024² 也没用上） | **961（一样！）** | 18.0 fps |

**注意：low 档 draw call 数没变**，说明阴影 pass 的 draw 没被省掉（`world.updateEnvironment` 里 `shadowMap.needsUpdate` 仍会触发一次全量阴影重绘），只是关了实时阴影采样。low 档 +5.7 fps 的收益来自 **`shadowMap.enabled=false` 省掉的片元采样开销**，不是省 draw call。这提示一个**明显的优化点：阴影刷新频率可以再降**（现在有 3 处 `needsUpdate = true`，`app.js:2356/2379` + `world.js` 太阳角度变化）。

## 6. 优化方案（三档）

### A 档 —— 不改观感

| 措施 | 预计收益 | 代价 | 证据支撑 |
| --- | --- | --- | --- |
| **A1 用独显跑 DSH**（Windows 图形设置 → `DeepSeek.exe` → 高性能；或 NVIDIA 控制面板加程序） | **最大单项，预计 3–6×**（RTX 3060 移动版带这场景轻松 60 fps） | 笔记本功耗/发热上升，需要重启 DSH 生效 | §1.1/1.2 当前 renderer 是 Intel UHD |
| **A2 静态合批**：对不动的家具/书本/餐具用 `InstancedMesh` 或 `BufferGeometryUtils.mergeGeometries` 按材质分组 | 961 → 目标 **≤250 draw call**；预计 **+40~80% 帧率** | 要改 `world.js` 的构造方式，但外观零变化 | §3.1 961 draw/帧、§3.4 零 InstancedMesh |
| **A3 冻结静止物体**：`matrixAutoUpdate = false` + `matrixWorldNeedsUpdate` 只在需要时置 true | 省 CPU 矩阵计算（当前 CPU 只占 3.5 ms，收益小，但为 A2 铺路） | 无 | §3.2 |
| **A4 阴影刷新降频**：`shadowMap.autoUpdate=false` 已有，但 3 处 `needsUpdate=true` 可合并成「灯/太阳变化才刷一次」，并加 1 秒节流 | 预计 **+5~10%**（对应 low 档 +5.7 fps 的一半） | 阴影偶尔滞后一帧，肉眼无感 | §4.2 |
| **A5 关 MSAA**：`antialias: false`，改用 FXAA（可选）或直接接受锯齿（核显上 4×MSAA 很贵） | 预计 **+10~20%** | 边缘略见锯齿，观感轻微变化（算 A 档边界） | `app.js:86` |
| **A6 动作按需加载**：32 个 webm 只预取 idle+当前几个，其余在使用时 `preload='none'` | 首屏快 0.3–0.5 s；切动作仍会有 130–380 ms 卡顿 | 首次点某动作会顿一下 | §3.4 7 个已加载 / 32 个总计 |

**A 档合计预期：A1 单独就能解决老大体感；A2+A4+A5 在不换独显的机器上预计从 17 fps → 28~35 fps。**

### B 档 —— 略改观感

| 措施 | 预计收益 | 代价 |
| --- | --- | --- |
| **B1 pixelRatio cap 到 1.0**（当前 dPR=1 已经是 1.0，**在这台机器上无效**）；真正有效的是把渲染分辨率按 `1/0.75` 缩放再 CSS 放大 | 帧率 **×1.8**（对应 §4.1 的 632×403 实验 34.7 fps） | 画面变软，字和细线会糊 |
| **B2 关掉 13 个 PointLight 中非当前房间的**（只留鱼所在房间 + 太阳 + 半球光） | 预计 +10~20%（片元光照计算线性下降） | 别的房间会暗，切房间时重新点亮 |
| **B3 远景家具低模 LOD**：房间外的家具用简化几何 | 减少 draw call 与顶点 | 走近会看见变化 |

**B 档合计：17 fps → 30~40 fps，代价是画面变软 + 部分房间偏暗。**

### C 档 —— 大幅降级（也是以后桌面壁纸版的底子）

| 措施 | 目标 |
| --- | --- |
| 只渲染鱼（一个 plane + webm 视频贴图）+ 一张预渲染好的房间背景图 | 3–5 draw call / 帧，预计 **55–60 fps**，CPU/GPU 都轻松 |
| 保留交互（摸摸头/喂小鱼干）做成视频切换 | 观感从「3D 房间」变成「2.5D 房间」，但**老大要的「鱼在动、能互动」全在** |

**C 档代价**：失去相机自由移动、失去 3D 视角。但 memoria 里记着老大 2026-11-10 拍板的最终形态是**桌面壁纸**（鼠标穿透、鱼自己在桌面走动），C 档正好是那条路的骨架 —— 壁纸不需要 3D 漫游。

## 7. 推荐

1. **先试 A1（指定独显）** —— 零代码改动、收益最大、可回滚。如果老大体感够了，A2/A4/A5 可以不做。
2. 若 A1 不管用或不想让笔记本发热：**A2 合批 + A4 阴影降频 + A5 关 MSAA**，代码改动集中在 `world.js` 构造段和 `app.js:86-94`，**外观零变化**，预计 17 → 28~35 fps。
3. **B1（半分辨率渲染）作为兜底**：一行 `setPixelRatio(0.75)` 就能翻倍，代价是画面变软。
4. C 档留给桌面壁纸版，不在这间 3D 房间上做。

## 10. A1 档实测：指定独显（D20261111-fish-008）

> 老大 2026-11-11 22:15 拍板「先试改独显那一条」。本节记录实际做了什么、结果如何。
> 结论先说：**注册表已按规范写入且生效，但 WebGL 仍然落在 Intel UHD 核显上 —— 这台机器的显示器物理上接在核显上（混合输出），UserGpuPreferences 改不动 WebGL 的渲染设备选择。**

### 10.1 做了什么

### 10.3 为什么 renderer 没变 —— 硬件拓扑的硬结论

1. **显示器输出接在核显上**：`Win32_VideoController` 里只有 Intel UHD 有 `VideoModeDescription = 2560 x 1440 … 165Hz`，RTX 3060 的该字段为空 → 屏幕（含 DSH 窗口）由核显驱动。
2. **`nvidia-smi` 报 `display_active = Disabled`** → 独显当前不驱动任何显示器，处于纯计算/Optimus 混合模式。
3. **驱动列表里没有 NVIDIA 的显示适配器实例**：`HKLM\SYSTEM\CurrentControlSet\Control\Class\{4d36e968-…}` 下只有 `0001 = Intel(R) UHD Graphics` 和 `0002 = Microsoft Remote Display Adapter` —— 独显在这套驱动栈里是「渲染设备」而不是「显示设备」。
4. **`nvidia-smi` 里 DeepSeek 的进程一个都没有**，显存占用 197 MiB 全是系统/QQ 的 → DSH 确实没在独显上跑。
5. `UserGpuPreferences`（图形设置里的「高性能」）是 **DWM/显示优先级提示**，在 Optimus 混合输出机型上它影响的是「窗口呈现在哪块 GPU 上合成」，**不改变 WebGL 上下文绑定哪块适配器** —— Chromium/ANGLE 仍按系统默认适配器建上下文。这解释了为什么改了注册表、重启两次，renderer 还是 Intel。

### 10.4 那为什么帧率从 17 涨到了 32？

诚实交代：**不是换显卡换来的**，是这次重启顺带清掉了一批负载：

- 第一次测基线时，DSH 里正开着房间面板（同源 iframe 在渲染），等于**两份 3D 场景同时在跑**；改后测的是 `ego` 单开一个房间页。
- 第二次重启后我 `Stop-Process chrome` 杀光了 ego（9 个进程）再重起，浏览器干净冷启 → GPU 进程无历史负担。
- `nvidia-smi` 显示的独显占用 0%，说明这部分提速与独显无关。

所以：**17 → 32 fps 是「同一块核显、负载更轻」的结果，不是硬件升级。** 真实体感提升有限，且这一档数字不可当作 A1 生效的证据。

### 10.6 下一步真正能切到独显的路（按推荐顺序，都要老大点头）

| 方案 | 做法 | 预期 | 代价/风险 |
| --- | --- | --- | --- |
| **B1 电源模式** | 设置 → 系统 → 电源和电池 → 电源模式 → **最佳性能**；同时确认接通电源适配器 | 独显可被唤醒，但仍是混合输出，WebGL 未必切换 | 零风险，可随时改回 |
| **B2 笔记本厂商控制中心 → 独显直连/GPU 模式** | 本机是 `WIN-B6H1RB8CI5N` 的笔记本，需查厂商（可能是神舟/机械师/雷神一类）控制中心里的「独显直连 / dGPU only / MUX Switch」 | **唯一能把显示输出接上独显的办法**，接上后 ANGLE 会拿到 NVIDIA | 需重启；部分机型切换后核显省电特性关闭、发热上升 |
| **B3 NVIDIA 控制面板 → 管理 3D 设置 → 首选图形处理器 → 高性能 NVIDIA 处理器**（全局或为 DeepSeek.exe 建 profile） | NVIDIA 控制面板 → 程序设置 → 添加 `<DSH_INSTALL>\DeepSeek.exe` → 高性能 | 在部分机型上能改变 ANGLE 适配器选择 | 需重启；可能无效（同 10.3 第 5 条） |
| **B4 外接显示器直连独显** | 若机器有 HDMI/DP 口直连独显，外接屏后把 DSH 拖到外接屏 | 该屏上的窗口由独显驱动 | 要有外接屏 |
| **B5 放弃换卡，做 A2 合批** | 见 §6 A2（InstancedMesh 合批 961→250 draw call + 阴影降频 + 关 MSAA） | 核显上预计 28~35 fps，外观零变化 | 要改 `world.js`，属于「改屋子」范畴，需老大单独点头 |

**我的建议**：先试 **B1（零风险）**；若无变化，直接用 **B5（A2 合批）** —— 因为 B2/B3/B4 都受制于这台机器的混合输出拓扑，而 B5 是我能完全控制的、且报告 §6 已算出 17→28~35 fps 的预期。
