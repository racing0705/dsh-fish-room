## 1. 取件过程（关键：上一轮为什么失败）

上一轮 11 个坏包的病因找到了，**不是网络全断，是 codeload 的 zip 有 4 字节偏移错误**：

- 所有下到的片段都有完整 zip 头和 15 个完整 local entry，只缺尾部中央目录 → Python 判 `BadZipFile`。
- 更关键的：`anime maid 3d model.glb`（58,885,308 B）在 local header 里写的 `crc/压缩后大小/解压后大小` 三个字段全被写成「+4」的值，就算下全了 zipfile 也解不开。
- 根因判断：codeload 流式打包时把「已写字节数」当成了条目长度，差一个 zip 本地头后续字段的 4 字节。

**真正的解法不是修 zip，是换通道：**

| 通道 | 结果 |
| --- | --- |
| `codeload.github.com` 直连 | 每秒 ~30 KB，跑满 900 秒下不完（30 MB 压缩体要 17 分钟以上），且必然被掐 |
| `https://ghproxy.net/…` | 25 秒只给 299 KB（限速更狠） |
| `https://ghfast.top/…` | 25 秒 21.4 MB（可用但慢） |
| **`https://gh-proxy.com/https://github.com/sh2234113/feiyu-room-template/archive/refs/heads/main.zip`** | **27.7 秒下完 86.9 MB，完整可解** ✅ |

一行命令：

```bash
curl -sL --max-time 300 -o repo.zip \
  https://gh-proxy.com/https://github.com/sh2234113/feiyu-room-template/archive/refs/heads/main.zip
```

> 记一笔：`_dl\fix_download.py` 那条「自己重写 local header + 补中央目录」的修复路线是对的但没必要——慢的是通道，不是算法。以后遇到 GitHub 大文件下载，先试 `gh-proxy.com` 再谈修包。

## 3. 暴喵 AI 领 token 的分步操作单（老大照点）

**前置**：这一步和装房间**其实可以解耦**——房间本体只需要 DSH 连着的任意可用模型。暴喵 token 的作用是把 DSH 的模型换成暴喵的 API，属于「作者推荐的省钱路线」，不是硬门槛。我们**已经用本机现有的 `deepseek-official / deepseek-flash` 跑通**，不领 token 也能用。

要省 token 就走这条：

1. 打开暴喵 AI 官网（作者简介里写的是「暴喵AI口令（111）可以免费领token」），注册/登录（大概率要微信扫码）。
2. 进「令牌 / API Key / 兑换」页面，找输入框，输入 `111`，点兑换。
3. 兑换成功后会得到两种东西之一：
   - **API Key**（形如 `sk-xxxxxxxx…`）→ 用于填进 DSH 的模型供应商配置，或 `config.json` 的 `dsh.authToken`。
   - **账号赠金**（不是 key）→ 那只需在 DSH 里把 provider 切成暴喵的 OpenAI 兼容端点，不用手动填 key。
4. **凭证不要贴进聊天**。在 DSH 桌面端「设置 → 模型/供应商」里直接填，或在 `config.json` 的 `dsh.authToken` 里填。填完自己验证：`curl -sI <暴喵端点>` 能 200 就说明通了。

> 作者的 `config.example.json` 里已经预置了 `baomiao-oneapi` 作为 fallback provider，模型名 `DeepSeek-V4.1-Flash 1017(1.20x)`——也就是说作者自己就是用暴喵跑的。我们的 `config.json` 里保留了这段 fallback 但主 provider 用本机的 `deepseek-official`。

**两项失败是同一个，且是 Windows 平台误报，不是真故障：**

```
✗ save / load 原子落盘，0600 权限
  Expected values to be strictly equal:
  438 !== 384
```

`438 = 0o666`、`384 = 0o600`。源码 `src/room-state.js:130` 和 `src/home-state.js:613` 都写了 `fs.writeFileSync(tmp, …, { mode: 0o600 })`，但 **Windows 的 NTFS 不支持 POSIX 权限位，`fs.statSync().mode` 恒返回 `0o666`**，所以这个断言在 Windows 上必然失败。
Windows 上真正的保护是 ACL —— 实测 `icacls state/home.json` 为 `Administrators:(F)` / `SYSTEM:(F)` / `Administrator:(F)` 且带 `(I)` 继承标记，即只有本机管理员可读写，**等效于 0600**。无需修。
